## Overview

Bookora is a BookMyShow‑style ticket booking application built with a **Flask** backend, a **MySQL** database, and a **server‑rendered vanilla‑JavaScript** frontend. Users log in without a password — they receive a one‑time code by email — then browse now‑showing movies, view showtimes across theatres, select seats from a live seat map, and confirm a booking. Behind the scenes the server owns everything that matters: it authenticates the user with a signed session cookie, prices the booking itself, and locks seats inside a database transaction so the same seat can't be sold twice.

It was built as a portfolio project to demonstrate practical full‑stack fundamentals: relational schema design, a REST‑style API, transactional booking logic, and a real authentication flow — without leaning on a heavyweight frontend framework.

## Key Features

- **Passwordless Email‑OTP login** — a 6‑digit code is emailed via Gmail SMTP; no passwords are stored.
- **Server‑side sessions** — the logged‑in user is tracked with a Flask signed cookie, so identity is never trusted from the client.
- **Movie catalogue** — now‑showing movies with posters, banners, cast, genre, certification, and trailers.
- **Showtimes across theatres** — schedules generated for the next 7 days across multiple Ahmedabad theatres.
- **Interactive seat selection** — a live seat map with tiered pricing (regular / premium / VIP) and already‑booked seats disabled.
- **Transactional booking** — seats are locked and priced on the server; double‑booking is prevented.
- **My Bookings** — view booking history and cancel a booking (which releases the seats).
- **Saved movies & profile** — bookmark movies and manage a lightweight profile.

## Architecture

Bookora is a classic three‑tier web application. The browser talks to Flask over HTTP; Flask renders the HTML pages and also exposes a JSON API that the page scripts call with `fetch`; Flask is the only thing that talks to MySQL.

```
┌─────────────────────────┐        ┌──────────────────────────┐        ┌─────────────────┐
│         Browser         │  HTTP  │        Flask (app.py)      │  SQL   │      MySQL       │
│  HTML + Bootstrap + JS  │ ─────► │  Page routes  +  JSON API  │ ─────► │   8 tables       │
│  fetch() to /api/...    │ ◄───── │  session cookie (signed)   │ ◄───── │  (XAMPP)         │
└─────────────────────────┘        └──────────────────────────┘        └─────────────────┘
```

The whole backend lives in a single, readable `app.py`: a `get_db()` connection helper, a `get_current_user()` / `login_required` pair that enforces authentication, the page routes, and the JSON API endpoints. Seat and booking data is generated by two seed scripts so the app has realistic content to run against.

## Authentication Flow

Login is passwordless and email‑based:

1. **Request a code** — the user enters their email; `POST /api/send-otp` generates a random 6‑digit OTP, stores it in the `otp_verification` table with an expiry timestamp, and emails it through Gmail SMTP.
2. **Verify the code** — `POST /api/verify-otp` checks the code against the database and its expiry. For a returning user this logs them in immediately; a new user continues to profile setup.
3. **Complete profile (new users)** — `POST /api/complete-profile` creates the user record.
4. **Session established** — on successful verification the server stores the user id in a **Flask signed session cookie** (`HttpOnly`, `SameSite=Lax`, `Secure` in production, 7‑day lifetime). Because the cookie is signed with the app's `SECRET_KEY`, the client cannot forge or tamper with it.
5. **Protected requests** — every user‑owned endpoint is wrapped with `@login_required` and reads the acting user from the session, never from the request body or URL.
6. **Logout** — `POST /api/logout` clears the session.

## Database Overview

MySQL, eight tables. Movies play at theatres via **shows**; each show owns a set of **seats**; a **booking** ties a user to a show and the seats they bought.

| Table | Purpose |
| --- | --- |
| `movies` | Movie catalogue (title, slug, genre, cast, poster/banner, trailer, certification). |
| `theatres` | Cinemas (seeded with four Ahmedabad venues). |
| `shows` | A movie playing at a theatre on a given date/time (FKs → `movies`, `theatres`). |
| `seats` | Per‑show seats with label, price, and booked status (FK → `shows`). |
| `users` | Accounts created via OTP login (email/phone, optional profile). |
| `otp_verification` | Short‑lived login codes with expiry. |
| `saved_movies` | Junction table for a user's bookmarked movies (users ↔ movies). |
| `bookings` | A confirmed/cancelled booking (FKs → `users`, `shows`; seats stored as JSON, with a server‑computed total). |

Foreign keys use `ON DELETE CASCADE`, and uniqueness constraints (e.g. one seat label per show, one save per user‑movie) keep the data consistent.

## Booking Workflow

```
Browse movies → Movie details → Showtimes → Seat selection → Log in (Email OTP) → Confirm → My Bookings
```

When the user confirms, `POST /api/create-booking` does the important work **on the server**, inside a transaction:

1. Opens a database transaction and **locks the requested seats** with `SELECT ... FOR UPDATE`.
2. Verifies every seat exists, belongs to the show, and is still available.
3. **Computes the total price itself** by summing the seats' prices — the amount sent by the client is ignored.
4. Inserts the booking, marks the seats as booked (recording who booked them and when), and commits.

If anything fails, the transaction rolls back so no partial booking is left behind. Cancelling a booking (`POST /api/cancel-booking`) is scoped to the owner and releases the seats back to available.

## Security Highlights

- **Server‑authoritative identity** — the logged‑in user comes from a signed session cookie, so tampering with a request body or URL can't let one user act as another (an IDOR‑safe design).
- **Parameterized SQL everywhere** — all queries use bound parameters, protecting against SQL injection.
- **Transactional, server‑priced bookings** — row locking (`FOR UPDATE`) prevents double‑booking and the server never trusts a client‑supplied price.
- **Hardened session cookie** — `HttpOnly`, `SameSite=Lax`, `Secure` (in production), with a bounded lifetime.
- **Time‑limited OTPs** — codes are generated server‑side and expire.
- **Secrets in `.env`** — no credentials in the codebase; `.env.example` ships placeholders only and `.env` is git‑ignored.
- **CORS allow‑list** — cross‑origin access is restricted to explicit origins.

## Getting Started

Full step‑by‑step instructions (with phpMyAdmin screenshots‑worthy detail and troubleshooting) are in **[SETUP.md](SETUP.md)**. The short version:

```bash
# 1. Start MySQL (and Apache for phpMyAdmin) from the XAMPP Control Panel

# 2. Create the database + tables + theatres
#    Import database_schema.sql via phpMyAdmin, or:
"C:\xampp\mysql\bin\mysql.exe" -u root < database_schema.sql

# 3. Install Python dependencies
python -m venv venv
venv\Scripts\activate            # Windows  (use: source venv/bin/activate on macOS/Linux)
pip install -r requirements.txt

# 4. Configure environment
copy .env.example .env           # then fill in your Gmail App Password + a SECRET_KEY

# 5. Seed data — ORDER MATTERS:  schema → movies → shows/seats
python seed_movies.py            # loads movies from movies-data.json
python seed_shows.py             # generates shows + seats (needs movies + theatres first)

# 6. Run
python app.py                    # → http://localhost:5000
```

### Prerequisites

- **XAMPP** (for MySQL + phpMyAdmin)
- **Python 3.10+** and `pip`
- A **Gmail account with an App Password** (2‑Step Verification enabled) so the app can send OTP emails

### Seed order (important)

The data must be created in this order, because each step depends on the previous one:

1. **`database_schema.sql`** → creates the `bookora` database, all tables, and the theatres.
2. **`seed_movies.py`** → loads the movies.
3. **`seed_shows.py`** → generates showtimes and seats for the existing movies and theatres.

Running the show seeder before the movie seeder produces no shows.

## Testing

Authorization tests live in `test_authorization.py`. They verify that protected endpoints reject unauthenticated requests and that every user‑owned action is scoped to the session user (not a client‑supplied id). With the Python dependencies installed, run:

```bash
python -m unittest test_authorization -v
```

The tests mock the database layer, so they need Flask installed but **do not** require a running MySQL server.

## Known Limitations & Future Improvements

- **No real payment gateway** — booking confirmation simulates payment rather than charging a card.
- **Demo email delivery** — OTP emails rely on a personal Gmail App Password over SMTP; a transactional email provider (SendGrid, SES) would be the production choice.
- **No OTP rate‑limiting** — adding per‑email / per‑IP throttling would harden the login flow against abuse.
- **Single‑file backend** — `app.py` is intentionally kept in one file for readability; splitting into blueprints/modules would scale better.
- **Seed data is regional** — theatres and movies are sample data (Ahmedabad); real deployments would source these dynamically.
- **Possible enhancements** — admin dashboard for managing movies/shows, booking confirmation emails, and screenshots/CI in the repo.
